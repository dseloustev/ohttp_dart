# Расширить покрытие тестами OHTTP и зафиксировать interop-ловушки в комментариях

**Оценка:** 1d
**Приоритет:** P2: High
**Компонент:** App
**Severity:** HIGH

## Описание задачи

`test/ohttp_test.dart` сейчас 165 строк; он покрывает `OhttpKeyConfig.parse`/`validate`, структуру encapsulate, плюс short-circuit decap, но без end-to-end round-trip encap → decap с синтетическим respondент'ом со стороны гейтвея, без пути ошибки аутентификации AEAD и без граничных входов (пустые / завышенные нагрузки). Каждый пробел позволяет регрессии прийти молча в кодовых путях, центральных для ценности библиотеки.

Параллельно с тестами, два существующих блока комментариев в `lib/src/ohttp.dart` (заметка про пустой AAD на строке 148 и заметка про обычный HKDF на строке 192) слишком кратки, чтобы остановить добронамеренный «фикс» от будущего мейнтейнера. Текущая реализация намеренно отклоняется от одного из прочтений RFC 9458 §4.3 (использует пустой AAD вместо OHTTP-заголовка), чтобы совпасть с референсной Go-реализацией, и намеренно использует обычный (unlabeled) HKDF в пути ответа по RFC 9458 §4.4, а не labeled-варианты, используемые в HPKE key schedule. Оба решения корректны, но неожиданны; оба защищены новым round-trip тестом из этой задачи и поставляемыми векторами.

## Технические детали

**1. Round-trip OHTTP encap → decap** (`test/ohttp_test.dart`)

Текущие тесты проверяют структуру вывода encap и логику short-circuit decap по отдельности. Добавить настоящий round-trip тест, который:

- Формирует шифротекст через `ohttpEncapsulate`.
- Запускает небольшой in-test хелпер, эмулирующий вывод секрета канала ответа на стороне гейтвея (использует те же примитивы, которые библиотека выставляет: `HpkeSender.hkdfExtract` / `hkdfExpand`).
- Шифрует подготовленный ответ выведенным секретом.
- Вызывает `ohttpDecapsulate` и проверяет, что расшифрованный plaintext в точности равен исходному.

Имя теста ссылается на RFC 9458 §4.3 и §4.4.

**2. Ошибка аутентификации AEAD** (`test/ohttp_test.dart`, после строки 163)

Строка 163 закрывает второй тест `ohttpDecapsulate`. Строки 217–225 в `lib/src/ohttp.dart` расшифровывают ответ через `aesGcm.decrypt(...)`, который бросает `SecretBoxAuthenticationError` на ошибке аутентификации (или обёрнутое `OhttpDecryptionException`, когда придёт задача по типизированной иерархии исключений).

Добавить тест, который формирует корректный encap, выводит секрет ответа как в шаге 1, шифрует ответ, затем переворачивает один байт шифротекста перед вызовом `ohttpDecapsulate`. Проверить, что decap бросает — сначала тип из cryptography, а после прихода типизированной иерархии — библиотечную обёртку. Написать тест так, чтобы он фиксировал текущее поведение и чисто обновлялся при смене типа исключения. Имя теста ссылается на RFC 9458 §4.4 и семантику аутентификации AEAD.

**3. Граничные входы** (`test/ohttp_test.dart`)

Граничные входы — пустая BHTTP-нагрузка, однобайтовая нагрузка, нагрузка на границе лимитов из задачи по усилению парсера — выявляют тонкие баги в коде обработки длин, которые happy-path тесты не ловят.

Добавить тесты, покрывающие:
- `ohttpEncapsulate` с пустым `binaryRequest` — определить ожидаемое поведение (вероятно, успешно формирует минимальный шифротекст).
- `ohttpDecapsulate` с пустым payload'ом ответа — ожидать типизированное исключение.
- Round-trip с нагрузкой ровно на настроенном лимите размера ответа (успех) и на один байт выше (ожидать отказ).

Если лимиты размеров из задачи по усилению парсера ещё не пришли, граничные тесты фиксируют текущее поведение и обновляются с приходом лимита. Тесты ссылаются на RFC 9458 §4.3 / §4.4, где применимо.

**4. Комментарий-предостережение о пустом AAD** (`lib/src/ohttp.dart:148-150`)

Текущая строка 148: `// Seal with empty AAD (per reference Go implementation, not RFC header)`. Расширить блок комментариев до:

1. Ссылка на RFC 9458 §4.3 и объяснение, что формулировка неоднозначна (живой вопрос: пустой AAD vs заголовок-как-AAD).
2. Ссылка на референсную Go-реализацию (URL или конкретный commit) как источник истины для выбора пустого AAD.
3. Указание, что поставляемые тесты полагаются на пустой AAD и что смена этого без скоординированных изменений на гейтвее — это разрыв wire-формата.
4. Cross-reference на блок комментариев про обычный HKDF (шаг 5 ниже) как companion-ловушку в том же файле.

Мейнтейнер, читающий комментарий, должен иметь возможность решить, не сломает ли предлагаемое изменение interop, без дополнительного research'а.

**5. Комментарий-предостережение о plain HKDF** (`lib/src/ohttp.dart:192-207`)

Строки 192–207 — блок plain HKDF в `ohttpDecapsulate`. Существующий комментарий на строке 192 (`// prk = HKDF-Extract(salt, secret) — plain HKDF, not labeled`) намекает на суть, но не описывает последствия. Расширить блок до:

1. Ссылка на RFC 9458 §4.4.
2. Указание ловушки: замена `HpkeSender.hkdfExtract` / `hkdfExpand` на labeled-варианты, используемые в HPKE key schedule, даст другой ключевой материал и сломает расшифровку против любого реального гейтвея — и изменение пройдёт молча, поскольку labeled-вариант всё равно даст валидный (но неправильный) результат.
3. Указание, что это намеренно и требуется RFC.
4. Cross-reference на блок комментариев про пустой AAD (шаг 4 выше) как companion-ловушку в том же файле.

Мейнтейнер, пробегающий функцию, не сможет случайно «гармонизировать» обычный HKDF в labeled, не отбросив предупреждение.

## AC

- Новый end-to-end round-trip тест прогоняет всю цепочку encap → вывод секрета ответа → шифрование ответа → decap в `test/ohttp_test.dart`; хелпер самодостаточный; расшифрованный plaintext в точности равен исходному.
- Новый тест с испорченным шифротекстом добавлен после строки 163; проверяет, что decap бросает исключение (точный тип — по текущему статусу работы по типизированной иерархии).
- Новые граничные тесты покрывают пустой `binaryRequest`, пустой payload ответа, нагрузку на лимите и нагрузку выше лимита.
- Блок комментариев в `lib/src/ohttp.dart:148-150` расширен до как минимум четырёх пунктов, перечисленных для заметки про пустой AAD; включает URL или ссылку на commit референсной Go-реализации.
- Блок комментариев в `lib/src/ohttp.dart:192-207` расширен до как минимум четырёх пунктов, перечисленных для заметки про plain HKDF.
- Имена всех новых тестов ссылаются на релевантную секцию RFC.

## Дополнительно

- Тесты: юнит-тесты в `test/ohttp_test.dart`; хелпер round-trip теста заодно служит документацией контракта канала ответа.
