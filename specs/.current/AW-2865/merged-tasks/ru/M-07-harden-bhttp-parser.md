# Усилить парсер BHTTP (проверки границ, лимиты размеров, статус-код, лимит запроса)

**Оценка:** 2d
**Приоритет:** P2: High
**Компонент:** App
**Severity:** HIGH

## Описание задачи

В `lib/src/bhttp.dart` есть четыре перекрывающихся пробела в устойчивости парсера, которые в сумме делают библиотеку уязвимой к крэшам, DoS и тихому приёму некорректного ввода от вредоносного или скомпрометированного гейтвея. Кошелёк, доверяющий гейтвею только в рамках криптографических гарантий, всё равно нуждается в том, чтобы BHTTP-слой корректно падал на чём угодно за рамками спецификации:

1. **`RangeError` вместо `FormatException`**: `decodeVarint` (строки 44–67) и вызовы `sublist` на строках 173, 178 и 187 бросают `RangeError` на обрезанном вводе. `RangeError` — это `Error`, а не `Exception`, поэтому вызывающий код, оборачивающий парсинг BHTTP в `try { ... } on FormatException { ... }` — естественная идиома Dart, — его не поймает, и программа упадёт.
2. **Нет лимитов размеров заголовков/тела ответа**: `parseResponse` (строки 164–187) читает `headersLen` и `contentLen` как сырые varint. Вредоносный гейтвей может объявить `headersLen = 2^30`, форсируя ~1 ГиБ-аллокацию в `data.sublist(...)` на строке 173 или 178. Аналогично, на стороне клиента `gatewayResponse.bodyBytes` передаётся в `ohttpDecapsulate` в `lib/src/ohttp_client.dart:129-133` без проверки длины. На мобильном кошельке даже под-OOM аллокация в сотни МиБ достаточна, чтобы завершить приложение.
3. **Нет лимита размеров на входы `serializeRequest`**: на строках 74–111 нет верхней границы на `method`, `scheme`, `authority`, `path`, `headers` или `body` перед varint-кодированием. Случайный баг в коде кошелька, который передаёт многомегабайтное тело, формирует огромный BHTTP-запрос, шифротекст и POST на гейтвей до того, как упадёт.
4. **Нет проверки диапазона статус-кода**: строки 148–162 читают `statusCode` как сырой varint и пропускают только informational `1xx`. Некорректный или вредоносный ответ может нести статус 999, 0 или `2^62 - 1`, и `parseResponse` спокойно его вернёт. Код кошелька, ветвящийся по статус-коду, может вести себя непредсказуемо.

Ссылки на RFC: RFC 9292 §3.3 (framing), §3.5.3 (response framing), §3.5.4 (varint через RFC 9000 §16); RFC 9110 §15 (диапазон статус-кодов).

## Технические детали

**1. Хелпер для проверки границ** (`lib/src/bhttp.dart:44-67, 173, 178, 187`)

Ввести приватный хелпер (например, `_requireBytes(data, offset, n)`), который бросает `FormatException` с понятным сообщением при `offset + n > data.length`. Применить перед каждым индексным чтением (`data[offset]`, `data[offset + i]`) и вызовом `sublist(...)` в `decodeVarint` и в путях парсинга response/request. Изменение механическое и локализованное; API-изменений нет — только замена `RangeError` на `FormatException` для этих конкретных мест.

**2. Лимиты размеров ответа** (`lib/src/bhttp.dart:164-187`, `lib/src/ohttp_client.dart:129-133`)

Применить два слоистых лимита с разумными дефолтами, подходящими для RPC-нагрузок кошелька (одни цифры МиБ максимум), оба настраиваемые:

- BHTTP-слой: в `parseResponse` сверять `headersLen` и `contentLen` с настроенной верхней границей до аллокации. Отклонять завышенные значения `FormatException` (через хелпер из шага 1).
- Слой OHTTP-клиента: в `OhttpClient.send` (строки 129–133) сверять `gatewayResponse.bodyBytes.length` с настроенной верхней границей до передачи в `ohttpDecapsulate`. Отклонять типизированным библиотечным исключением.

**3. Лимиты размеров запроса** (`lib/src/bhttp.dart:74-111`)

Применить настраиваемые верхние границы на входы `serializeRequest` (`method`, `scheme`, `authority`, `path`, количество и длины заголовков, длина `body`) до начала сериализации. Отклонять завышенные значения типизированным библиотечным исключением. Дефолты консервативные и задокументированные; RPC-нагрузки кошелька редко превышают несколько сотен КБ.

**4. Проверка диапазона статус-кода** (`lib/src/bhttp.dart:148-162`)

После чтения финального (не-informational) статус-кода сверять, что он попадает в 100–599 включительно (RFC 9110 §15). На out-of-range бросать `FormatException`. Зафиксировать ограничение в doc-комментарии `parseResponse`.

**5. Тесты** (`test/bhttp_test.dart`)

Добавить тесты в группу parsing response:
- Обрезанный ввод по каждому упомянутому смещению: 1-байтовая граница varint, 2/4/8-байтовая граница varint, имя заголовка, значение заголовка, тело. Проверять `FormatException` (а не `RangeError`).
- Завышенный `headersLen` → `FormatException`.
- Завышенный `contentLen` → `FormatException`.
- Завышенное тело ответа на уровне клиента → типизированное библиотечное исключение.
- Статус-код: 100 (принять после informational skip), 200 (принять), 599 (принять), 600 (отклонить), 99 (отклонить), `2^62 - 1` (отклонить).
- `serializeRequest` отклоняет каждый класс перебора границ.

## AC

- Все операции `data[offset]`, `data[offset + i]` и `data.sublist(...)` в парсере BHTTP проходят через общий хелпер проверки границ или имеют эквивалентный guard, и бросают `FormatException` (никогда `RangeError`) на обрыве.
- `try { ... } on FormatException { ... }` корректно ловит каждый сценарий обрыва.
- `parseResponse` отклоняет секции заголовков и контента, превышающие настроенные лимиты, через `FormatException`; дефолты консервативно низкие и задокументированы.
- `OhttpClient.send` отклоняет ответы гейтвея, превышающие настроенный лимит, до парсинга.
- `serializeRequest` отклоняет входы, превышающие настроенные верхние границы для method/scheme/authority/path/headers/body, типизированным библиотечным исключением.
- `parseResponse` отклоняет статус-коды вне 100–599 через `FormatException`; doc-комментарий ссылается на RFC 9110 §15.
- Юнит-тесты покрывают каждый сценарий, перечисленный в «Тестах» выше.

## Дополнительно

- Тесты: исчерпывающие негативные юнит-тесты для парсера; позитивные тесты на граничные случаи (статус 100/200/599; cap-1/ровно cap/cap+1).
- Поверхность настройки лимитов должна совпадать с тем, какую структуру настроек вводят другие задачи на клиенте (свести в одно место).
