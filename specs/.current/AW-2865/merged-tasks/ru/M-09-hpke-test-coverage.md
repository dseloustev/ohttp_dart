# Расширить покрытие тестами HPKE (overflow, некорректный public key, границы export)

**Оценка:** 1d
**Приоритет:** P2: High
**Компонент:** App
**Severity:** HIGH

## Описание задачи

`test/hpke_test.dart` покрывает векторы RFC 9180 Appendix A.1 через хук инъекции `testKeyPair` в `setupBaseS` и небольшой набор happy-path тестов, но оставляет три значимых негативных пути без проверки. Каждый пробел позволяет регрессии прийти молча и подрывает криптографические гарантии, которые библиотека должна обеспечивать. Хотя нормальный OHTTP-поток ни одного из этих условий не достигает (one-shot seal, гейтвей-предоставляемый публичный ключ), нижележащая машинерия существует и может быть задействована будущими кодовыми путями или вредоносными входами от гейтвея.

## Технические детали

**1. Overflow счётчика sequence в `HpkeSenderContext.seal`** (`test/hpke_test.dart`, после строки 200)

`HpkeSenderContext.seal` вычисляет nonce на каждый вызов через XOR `_seq` с `baseNonce`. RFC 9180 §5.2 ограничивает sequence сверху значением `2^(8*Nn) - 1`; на overflow реализация обязана отказаться продолжать seal. Переиспользование nonce в AES-GCM после overflow катастрофично. Текущие тесты `seal seq=0` и `seal seq=1` заканчиваются около строки 200; теста на overflow нет.

Добавить тест, который:
- Принудительно ставит `_seq` в `2^(8*Nn) - 1`.
- Один раз успешно вызывает `seal`.
- Снова вызывает `seal` и проверяет, что вызов падает с библиотечным исключением (не голым `Error`).

Если текущая реализация не enforce'ит лимит, область расширяется до фикса в `hpke.dart`. Имя теста ссылается на RFC 9180 §5.2.

**2. `setupBaseS` с некорректным public key** (`test/hpke_test.dart`)

`setupBaseS` принимает public key получателя, но ни один существующий тест не подаёт ему вырожденное значение. Спецификация X25519 (RFC 7748 §6.1) помечает определённые low-order точки, для которых shared secret константен или нулевой. Кошелёк, получивший атакерски подобранный KeyConfig, может получить public key, специально выбранный так, чтобы дать известный shared secret.

Добавить тесты, вызывающие `setupBaseS` с:
- Полностью нулевым 32-байтовым public key.
- Каноническими X25519 low-order точками, перечисленными в RFC 7748 §6.1 / информационных рекомендациях HPKE.

Проверять ожидаемое поведение (отказ в `setupBaseS` или — если ошибку поднимает слой X25519 — определённое библиотечное исключение). Если библиотека сейчас не отклоняет такие входы, область расширяется до валидации в `hpke.dart` или в потоке `OhttpKeyConfig.parse`/`validate`. Имя теста ссылается на RFC 7748 §6.1.

**3. `HpkeSenderContext.export` с некорректной длиной** (`test/hpke_test.dart`, после строки 241)

Строка 241 — последняя `});` теста `export with "TestContext"`. Группа `HPKE RFC 9180` закрывается на строке 242. RFC 9180 §5.3 ограничивает параметр длины `Export` значением `2^32 * Nh` байт; нулевая длина — определённый граничный случай; завышенные длины должны отклоняться.

Добавить тесты, покрывающие:
- `length == 0` — определить ожидаемое поведение (вероятно, возвращает пустой `Uint8List`).
- `length == Nh` — канонический случай (уже покрыт косвенно; явное assertion).
- `length > 2^32 * Nh` — ожидать библиотечное исключение.

Если реализация сейчас не enforce'ит лимит, область расширяется до валидации. Имена тестов ссылаются на RFC 9180 §5.3.

## AC

- Тест на overflow sequence добавлен после строки 200 в `test/hpke_test.dart`; покрывает границу `_seq == 2^(8*Nn) - 1` и случай overflow `_seq == 2^(8*Nn)`; проверяет библиотечное исключение. Если у кода нет лимита — включён фикс реализации.
- Тесты на некорректный public key добавлены; покрывают как минимум полностью нулевой 32-байтовый public key плюс low-order точки RFC 7748 §6.1; проверяют ожидаемое библиотечное исключение. Если у реализации нет валидации — включён фикс.
- Тесты на некорректную длину `export` добавлены после строки 241; покрывают `length == 0`, `length == Nh` и `length > 2^32 * Nh`; проверяют библиотечное исключение в случае перебора лимита. Если у реализации нет лимита — включён фикс.
- Все имена новых тестов ссылаются на релевантную секцию RFC.
