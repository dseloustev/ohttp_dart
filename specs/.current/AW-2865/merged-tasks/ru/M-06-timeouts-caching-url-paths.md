# Добавить HTTP-таймауты, кэширование KeyConfig и нормализацию URL-путей

**Оценка:** 2d
**Приоритет:** P2: High
**Компонент:** App
**Severity:** HIGH

## Описание задачи

У `OhttpClient.send()` есть три независимых пробела в network reliability, которые в сумме дают плохой UX для кошелька:

1. Ни GET KeyConfig (`_httpClient.get(...)` в `lib/src/ohttp_client.dart:81-83`), ни POST на гейтвей (`_httpClient.post(...)` в строках 115–119) не имеют `.timeout(...)`. Не отвечающий гейтвей может зависнуть `await` бесконечно. Для интерактивного UI кошелька это выглядит как «замёрзший» экран без индикатора прогресса и без способа выйти — пользователю остаётся убить приложение.
2. Нет кэша KeyConfig. Каждый `send()` запускает свежий discovery GET (строки 81–89), удваивая количество round trip на каждый RPC-вызов (обновление баланса, список транзакций, оценка комиссии). Для кошелька, который делает много вызовов подряд, это удваивает latency и трафик без пользы — KeyConfig это долгоживущий материал, который гейтвей намеренно ротирует редко. Библиотека также плохо относится к оператору релея, который видит два запроса на одну логическую операцию.
3. URL собирается конкатенацией строк в трёх местах (`lib/src/ohttp_client.dart:82, 116, 154`) без нормализации слешей. Если вызывающий код передаёт `gatewayBaseUrl: 'https://gw.example/'` и `configPath: '/key'`, получается `https://gw.example//key` — двойной слеш, который большинство серверов терпят, но строгий обратный прокси может отклонить. Зеркальный случай (нет завершающего слеша на базе, нет ведущего на пути) вообще пропускает разделитель.

## Технические детали

**1. Настраиваемые таймауты** (`lib/src/ohttp_client.dart:81-83, 115-119`)

Добавить `.timeout(...)` для обоих HTTP-вызовов в `OhttpClient.send()`. Разрешить переопределение через `OhttpGatewayConfig` (или новый объект `OhttpClientOptions`) с разумными значениями по умолчанию. Зафиксировать дефолты в doc-комментарии. На таймаут бросать библиотечное типизированное исключение.

Семантика повторов решается отдельно — как минимум зафиксировать в документации отсутствие автоматических повторов и ответственность вызывающего кода.

**2. Кэш KeyConfig с TTL** (`lib/src/ohttp_client.dart:69-89`)

Сейчас у `OhttpClient` только поля `_httpClient` и `gateway`. Добавить поле-кэш `KeyConfig?` с настраиваемым TTL. Hit'ы в кэш пропускают discovery GET. На ошибке, указывающей на устаревший конфиг (специальный код ошибки гейтвея или ошибка аутентификации AEAD на ответе), кэш инвалидируется и discovery повторяется один раз.

- TTL настраивается через `OhttpGatewayConfig` (или `OhttpClientOptions`); дефолт должен отражать реалистичный темп ротации ключей и быть задокументирован.
- Параллелизм: Dart однопоточный в рамках isolate; достаточно guard-future `Future<KeyConfig>`, чтобы перекрывающиеся `send()`-вызовы делили один in-flight fetch.

**3. Нормализация URL-путей** (`lib/src/ohttp_client.dart:82, 116, 154`)

Три места сейчас конкатенируют строки:
- Строка 82: `Uri.parse('${gateway.gatewayBaseUrl}${gateway.configPath}')`
- Строка 116: `Uri.parse('${gateway.gatewayBaseUrl}${gateway.requestPath}')`
- Строка 154: `Uri.parse('${gateway.effectiveDirectBaseUrl}$path')` (или её приватная замена, если задача по приватности `sendDirect` уже пришла)

Ввести единый хелпер, который нормализует обработку слешей (все четыре случая: база со слешем/без × путь со слешем/без) и проверяет, что полученный `Uri` корректен. Три места вызова делегируют хелперу.

## AC

- На обоих вызовах `_httpClient.get` и `_httpClient.post` в `OhttpClient.send` навешен `.timeout(...)` с настраиваемой длительностью.
- Дефолтный таймаут зафиксирован в doc-комментарии `OhttpGatewayConfig` (или `OhttpClientOptions`).
- Таймаут даёт типизированное библиотечное исключение (из той же иерархии, что используется в остальном коде клиента).
- У `OhttpClient` есть поле-кэш и настройка TTL для распарсенного `KeyConfig`.
- Первый `send()` заполняет кэш; последующие `send()` в пределах TTL пропускают discovery GET.
- TTL настраивается, дефолт отражает реалистичный темп ротации ключей; политика инвалидации кэша задокументирована.
- Единый хелпер обрабатывает сборку URL для GET KeyConfig, POST на гейтвей и direct-send; покрывает все четыре комбинации слешей и валидирует результат.
- Юнит-тесты покрывают: срабатывание таймаута на медленном моке; cache miss → заполнение; cache hit в пределах TTL → нет GET; истечение кэша → re-fetch; инвалидация по ошибке → re-fetch; сборку URL для каждой из четырёх комбинаций слешей.

## Дополнительно

- Тесты: юнит-тесты с моком `http.Client` для путей таймаутов и кэширования; чистые юнит-тесты для URL-хелпера.
- Производительность: cache hit должен наблюдаться в тестах как «ноль HTTP-вызовов на endpoint configPath».
