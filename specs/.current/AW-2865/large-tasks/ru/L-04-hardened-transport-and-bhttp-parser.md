# Защищённый транспорт: HTTP-таймауты, ограничение размера ответа на слое OHTTP + границы/ограничения парсера BHTTP

**Оценка:** 2,5 дня
**Приоритет:** P2: High
**Компонент:** App
**Серьёзность:** HIGH

## Описание задачи

Два парных направления работ по устойчивости к некорректно ведущему себя или вредоносному шлюзу. Оба бросают новые типизированные исключения в иерархию `OhttpException`, введённую в L-03; выполнение их вместе сохраняет поверхность конфигурации (таймауты, ограничения) консолидированной в одном месте, а не перетряхиваемой дважды.

**Две темы из исходной L-03 решаются реструктуризацией L-01 и исключаются из этой задачи:**
- **Кэширование KeyConfig** обеспечивается `KeyConfigCache` (TTL + single-flight де-дупликация + ручная инвалидация + инжектируемые часы), вводится L-01 вместе с политикой инвалидации `OhttpSession` при `OhttpHttpException`. Здесь дополнительной работы не требуется.
- **Нормализация путей URL** устранена L-01 — `HttpClientTransport` принимает `Uri keysUrl` и `Uri gatewayUrl` напрямую, никакой конкатенации строк `gatewayBaseUrl + configPath`. Проблема четырёх комбинаций слешей исчезла.

**Сетевая часть — у `HttpClientTransport` один пробел:**

1. Ни `_client.get(_keysUrl)` (в `HttpClientTransport.fetchKeyConfig`), ни `_client.post(_gatewayUrl, ...)` (в `HttpClientTransport.postToGateway`) не имеют цепочки `.timeout(...)`. Не отвечающий шлюз может бесконечно подвесить `await`. Для интерактивного UI кошелька это проявляется как замёрзший экран без индикации прогресса и без аварийного выхода.

**Оркестрационная часть — у `OhttpSession.send` один пробел:**

2. **Нет ограничения размера на байты ответа шлюза** до того, как они передаются в `ohttpDecapsulate`. Враждебный шлюз может вернуть тело в сотни МиБ; на мобильном кошельке даже sub-OOM выделение в сотни МиБ достаточно, чтобы убить приложение.

**Часть парсера — у `lib/src/bhttp.dart` четыре пересекающихся дефекта:**

3. **`RangeError` вместо `FormatException`**: `decodeVarint` (строки 44–67) и вызовы `sublist` на строках 173, 178 и 187 бросают `RangeError` на усечённом входе. `RangeError` — это `Error`, а не `Exception`, поэтому вызывающая сторона, оборачивающая парсинг BHTTP в `try { ... } on FormatException { ... }`, не поймает его, и программа упадёт.
4. **Нет ограничений на размер заголовков/тела ответа**: `parseResponse` (строки 164–187) читает `headersLen` и `contentLen` как сырые varint. Враждебный шлюз может объявить `headersLen = 2^30`, форсируя выделение ~1 ГиБ в `data.sublist(...)` на строке 173 или 178.
5. **Нет ограничения на размер входов `serializeRequest`**: строки 74–111 не накладывают верхнюю границу на `method`, `scheme`, `authority`, `path`, `headers` или `body` перед varint-кодированием.
6. **Нет валидации диапазона status-кода**: строки 148–162 читают `statusCode` как сырой varint и только пропускают информационные ответы `1xx`. Некорректный или вредоносный ответ шлюза может нести статус 999, 0 или `2^62 - 1`, и `parseResponse` спокойно его вернёт.

Ссылки на RFC: RFC 9292 §3.3 (фрейминг), §3.5.3 (фрейминг ответов), §3.5.4 (varint через RFC 9000 §16); RFC 9110 §15 (диапазон status-кодов); RFC 9458 §1 (транспорт).

## Технические детали

### Часть A — Сетевая часть (`lib/src/adapters/http/http_transport.dart`)

**1. Настраиваемые таймауты**

Добавить цепочки `.timeout(...)` к обоим вызовам `http.Client` в `HttpClientTransport`. Расширить конструктор:

```dart
HttpClientTransport({
  required http.Client client,
  required Uri keysUrl,
  required Uri gatewayUrl,
  Duration keysTimeout = const Duration(seconds: 10),
  Duration gatewayTimeout = const Duration(seconds: 30),
});
```

Задокументировать значения по умолчанию в doc-комментарии. По таймауту бросать `OhttpTimeoutException` (из иерархии L-03).

Отдельно принять решение о семантике retry — как минимум задокументировать отсутствие автоматических повторов и ответственность вызывающей стороны.

### Часть B — Оркестрационная часть (`lib/src/ohttp_session.dart`)

**2. Ограничение размера тела ответа**

В `OhttpSession.send`, после возврата `_transport.postToGateway(...)` и до вызова `ohttpDecapsulate`, проверять `gatewayResponseBytes.length <= _maxResponseBytes`. Отвергать с `OhttpParseException` (из иерархии L-03).

Сделать ограничение настраиваемым через конструктор `OhttpSession` (и `OhttpSession.withTransport`), с разумным wallet-RPC значением по умолчанию в диапазоне однозначных МиБ. Задокументировать значение по умолчанию.

### Часть C — Защита парсера BHTTP (`lib/src/bhttp.dart`)

**3. Хелпер для bounds-check** (строки 44–67, 173, 178, 187)

Ввести приватный хелпер (например, `_requireBytes(data, offset, n)`), который бросает `FormatException` с понятным сообщением при `offset + n > data.length`. Применять его перед каждым индексированным чтением (`data[offset]`, `data[offset + i]`) и вызовом `sublist(...)` в `decodeVarint` и в путях парсинга ответа/запроса. Изменение механическое и локализованное; никаких изменений API кроме замены `RangeError` на `FormatException` для этих конкретных мест вызова.

**4. Ограничения размера ответа в `parseResponse`** (строки 164–187)

Применить настраиваемые верхние границы на объявления `headersLen` и `contentLen` в `parseResponse` перед выделением. Отвергать чрезмерные объявления с `FormatException` (через хелпер из шага 3). Значения по умолчанию консервативно низкие (однозначные МиБ) и задокументированы; та же поверхность опций должна быть достижима через `OhttpSession`, чтобы вызывающая сторона конфигурировала ограничения в одном месте (значения по умолчанию на BHTTP-уровне существуют для прямых потребителей `bhttp.parseResponse`; `OhttpSession` пробрасывает своё настроенное ограничение при вызове парсера).

**5. Ограничения размера запроса в `serializeRequest`** (строки 74–111)

Применить настраиваемые верхние границы на входы `serializeRequest` (`method`, `scheme`, `authority`, `path`, количество и длины имён/значений заголовков, длина `body`) перед началом сериализации. Отвергать чрезмерные входы с `OhttpParseException` (или — если предпочтительно более строгое типизированное имя — `OhttpRequestTooLargeException`; согласовать именование с иерархией L-03). Значения по умолчанию консервативны и задокументированы; wallet RPC payload редко превышает несколько сотен килобайт.

**6. Валидация диапазона status-кода** (строки 148–162)

После чтения финального (неинформационного) status-кода валидировать, что он попадает в 100–599 включительно (RFC 9110 §15). Бросать `FormatException` для выходящих за диапазон значений. Документировать ограничение в doc-комментарии `parseResponse`.

### Часть D — Тесты

**7. Сетевые тесты** (`test/adapters/http_adapter_test.dart`):

- То же для `postToGateway` относительно настроенного `gatewayTimeout`.
- Исключение таймаута ловится как `on OhttpException`.

**8. Тесты сессии** (`test/ohttp_session_test.dart`):
- Ответ шлюза на один байт выше настроенного ограничения → `OhttpSession.send` бросает `OhttpParseException` до вызова `ohttpDecapsulate`.
- Ответ шлюза ровно на ограничении → проходит проверку ограничения (decap может упасть ниже по потоку; утверждать только то, что проверка ограничения пройдена).

**9. Тесты парсера** (`test/bhttp_test.dart`):
- Усечённый вход в каждом упомянутом смещении: однобайтовая граница varint, 2/4/8-байтовые границы varint, имя заголовка, значение заголовка, контент. Утверждать `FormatException` (не `RangeError`).

- Чрезмерное объявление `contentLen` → `FormatException`.
- Status-код: 100 (принять после пропуска информационного), 200 (принять), 599 (принять), 600 (отвергнуть), 99 (отвергнуть), `2^62 - 1` (отвергнуть).
- `serializeRequest` отвергает каждый класс входа сверх ограничения (method/scheme/authority/path/header-name/header-value/body) с типизированным библиотечным исключением.

## Критерии приёмки

**Таймауты:**
- Конструктор `HttpClientTransport` принимает настраиваемые длительности `keysTimeout` и `gatewayTimeout`; оба вызова `http.Client` цепляют `.timeout(...)`.
- Значения по умолчанию задокументированы в doc-комментарии конструктора; таймаут производит `OhttpTimeoutException` (из L-03).

**Ограничение размера ответа (слой OHTTP):**
- Конструктор `OhttpSession` (и `OhttpSession.withTransport`) принимает настраиваемое ограничение `maxResponseBytes` с задокументированным значением по умолчанию, подходящим для wallet RPC.
- `OhttpSession.send` отвергает тела ответов шлюза выше ограничения с `OhttpParseException` до вызова `ohttpDecapsulate`.

**Парсер BHTTP:**
- Все операции `data[offset]`, `data[offset + i]` и `data.sublist(...)` в парсере BHTTP проходят через общий хелпер bounds-check или эквивалентную защиту и бросают `FormatException` (никогда `RangeError`) при усечении.
- `try { ... } on FormatException { ... }` корректно ловит любой сценарий усечения.
- `parseResponse` отвергает секции заголовков и контент больше настроенных ограничений с `FormatException`; значения по умолчанию консервативно низкие и задокументированы.
- `serializeRequest` отвергает входы, превышающие настроенные верхние границы для method/scheme/authority/path/headers/body length, с типизированным библиотечным исключением.
- `parseResponse` отвергает status-коды вне 100–599 с `FormatException`; doc-комментарий ссылается на RFC 9110 §15.

**Тесты:**
- Unit-тесты покрывают каждый сценарий, перечисленный в разделе «Тесты» выше.

## Дополнительно

- Поверхность конфигурации ограничений размера для BHTTP-уровня (`parseResponse`, `serializeRequest`) — значения по умолчанию существуют на уровне BHTTP API; `OhttpSession` раскрывает собственное ограничение `maxResponseBytes` для проверки на слое OHTTP. Эти два слоя защищают от разных поверхностей атаки (чрезмерное объявление vs. чрезмерный фактический payload) и должны оставаться независимыми.
- Зависит от L-01 (типы `HttpClientTransport`, `OhttpSession` и `KeyConfigCache` не существуют до приземления реструктуризации; `bhttp.dart` не меняется в L-01, но ограничение на слое OHTTP принадлежит новому `OhttpSession`).
- Зависит от L-03 (использует `OhttpTimeoutException`, `OhttpParseException` из типизированной иерархии).
- Дополнения BHTTP-тестов из L-06 (случаи усечения, утверждающие `FormatException`) предполагают, что работа по защите парсера в этой задаче выполнена.
- Исключено из исходной L-03 (теперь обрабатывается L-01): кэширование KeyConfig с TTL (теперь `KeyConfigCache`), нормализация путей URL для GET KeyConfig / POST на шлюз / direct-send (путь direct-send больше не существует; остальные два теперь принимают `Uri` напрямую).
- Исходные merged-задачи (в `../merged-tasks/`): M-06 (таймауты/кэширование/URL) — половины с кэшированием и URL поглощены L-01; M-07 (защита парсера BHTTP) — полностью сохранено здесь, плюс ограничение размера ответа на слое OHTTP, которое ранее жило на `OhttpClient.send`.
