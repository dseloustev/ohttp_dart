# Валидация входов для `HttpClientTransport` и `OhttpRequestData`

**Оценка:** 1,5 дня
**Приоритет:** P2: High
**Компонент:** App
**Серьёзность:** HIGH

## Описание задачи

После реструктуризации L-01 две поверхности конструирования находятся на границе доверия между кошельком (или любым потребителем) и relay/шлюзом: `HttpClientTransport` (хранит URL шлюза) и `OhttpRequestData` (несёт authority цели внутреннего BHTTP). Обе сейчас принимают сырые строки/URI без валидации:

1. **Нет валидации схемы у `keysUrl` / `gatewayUrl`** (конструктор `HttpClientTransport`). RFC 9458 §1 требует TLS на внешнем канале между клиентом и relay. Кошелёк с опечаткой в конфигурации или с неправильно настроенным staging-URL мог бы молча откатиться на `http://`, передавая внешний OHTTP-шифротекст в открытом виде — давая пассивному наблюдателю на пути возможность корреляции по таймингу с шлюзом и подрывая свойство unlinkability, ради которого OHTTP и существует.

2. **Нет валидации формы `authority`** (конструктор `OhttpRequestData`; также извлекается из `request.url` внутри `OhttpHttpClient.send`). Поле встраивается дословно во внутренний BHTTP-запрос через `bhttp.serializeRequest`. Некорректное значение (`"https://host"`, пробелы в начале/конце, встроенный путь) молча приводит к некорректному внутреннему BHTTP-запросу, и потребитель не получает никакого сигнала, пока шлюз не вернёт ошибку парсинга.

Некастодиальный крипто-кошелёк, попавший в любой из этих режимов отказа, не получает никакого рантайм-предупреждения о том, что развёртывание сломано — пока трафик уже не начнёт перехватываться или пока шлюз не вернёт ошибку парсинга внутреннего запроса.

Примечание: обеспокоенность обходом приватности, поднятая в оригинальной L-01 (тихий fallback `sendDirect()` на `gatewayBaseUrl`), **решается реструктуризацией L-01** — `sendDirect()` и `OhttpGatewayConfig` больше не существуют. Потребитель, желающий plaintext HTTP в новой архитектуре, просто использует сырой `http.Client` и пропускает конструирование `OhttpHttpClient`. Больше нет единственной поверхности API, чьё имя предполагает «OHTTP», но молча отправляет plaintext. Оставшаяся работа — это чисто валидация входов на двух новых поверхностях конструирования.

## Технические детали

### Часть A — Принудительное использование схемы HTTPS (`HttpClientTransport`)

**1. Отвергать не-HTTPS схемы во время конструирования** (`lib/src/adapters/http/http_transport.dart`)

`HttpClientTransport({required http.Client client, required Uri keysUrl, required Uri gatewayUrl})` — единственное место, где URL шлюза входят в пакет. Валидировать оба URI во время конструирования:

- Отвергать любой `keysUrl.scheme != 'https'`.
- Отвергать любой `gatewayUrl.scheme != 'https'`.
- Бросать библиотечное исключение (`OhttpConfigException` или — если L-03 уже приземлила свою иерархию — соответствующий подкласс `OhttpException`; согласовать именование с L-03).

Задокументировать обоснование в doc-комментарии конструктора со ссылкой на RFC 9458 §1.

**2. Опциональный escape hatch для тестов**

Если нужен escape hatch только для тестов (например, фикстуры `MockClient`, использующие `http://localhost`), закрыть его явным именованным флагом (например, `allowInsecureScheme: false` по умолчанию). Production-пути кода не должны иметь возможности случайно через него проскочить. Задокументировать предполагаемый scope флага (только тестирование) в doc-комментарии параметра.

### Часть B — Валидация формы authority (`OhttpRequestData`)

**3. Валидировать `authority` во время конструирования** (`lib/src/ohttp_session.dart`)

`OhttpRequestData.authority` — это продукция `authority` из RFC 3986: `host` или `host:port`. Валидировать в конструкторе:

- Отвергать пустые значения.
- Отвергать значения, содержащие префикс схемы (`http://`, `https://`, всё, что соответствует `^[a-zA-Z][a-zA-Z0-9+.-]*://`).
- Отвергать значения, содержащие пробелы.
- Отвергать значения, содержащие символы пути / запроса / фрагмента (`/`, `?`, `#`).
- Бросать библиотечное исключение (`OhttpConfigException` или эквивалент — та же иерархия, что в части A).

Задокументировать ожидаемую форму в doc-комментарии конструктора со ссылкой на RFC 3986 §3.2.

**4. Валидация на стороне извлечения в `OhttpHttpClient`** (`lib/src/adapters/http/ohttp_http_client.dart`)

`OhttpHttpClient.send` уже извлекает `authority` из `request.url.host` (плюс логика порта). Поскольку извлечение проходит через `OhttpRequestData(...)`, валидация в конструкторе из части B покрывает этот путь автоматически — отдельный шаг валидации в адаптере не нужен. Проверить инспекцией, что адаптер не обходит конструктор (то есть не присваивает значение приватному полю напрямую).

### Часть C — Тесты

**5. Тесты валидации схемы** (`test/adapters/http_adapter_test.dart`)

Добавить кейсы:
- Корректные `https://gateway.example.com/keys` и `https://gateway.example.com/gw` — успех.
- `http://gateway.example.com/keys` для `keysUrl` — отвергается с типизированным исключением.
- `http://gateway.example.com/gw` для `gatewayUrl` — отвергается.
- `ftp://gateway.example.com/keys` — отвергается.
- `Uri` с пустой схемой — отвергается.
- Если добавлен escape hatch `allowInsecureScheme`, один позитивный тест с `allowInsecureScheme: true` и `http://` — успех; задокументировать, что это test-only флаг.

**6. Тесты валидации authority** (`test/ohttp_session_test.dart`)

Добавить кейсы для конструирования `OhttpRequestData`:
- Корректный `host.example.com` — успех.
- Корректный `host.example.com:8443` — успех.
- Пустая строка — отвергается.
- `https://host.example.com` (с префиксом схемы) — отвергается.
- `host.example.com /path` (пробел) — отвергается.
- `host.example.com/path` — отвергается.
- `host.example.com?q=1` — отвергается.
- `host.example.com#frag` — отвергается.

## Критерии приёмки

**Валидация схемы:**
- Конструирование `HttpClientTransport` с не-`https://` `keysUrl` или `gatewayUrl` бросает библиотечное исключение во время конструирования.
- Doc-комментарий конструктора ссылается на RFC 9458 §1 для требования схемы.
- Любой флаг escape hatch (если добавлен) по умолчанию выключен и задокументирован как test-only.

**Валидация authority:**
- Конструирование `OhttpRequestData` с пустым / с префиксом схемы / содержащим пробелы / содержащим путь / содержащим запрос / содержащим фрагмент `authority` бросает библиотечное исключение во время конструирования.
- Doc-комментарий конструктора ссылается на RFC 3986 §3.2 для формы authority.
- `OhttpHttpClient.send` проходит через `OhttpRequestData(...)` (не обходит конструктор), так что та же валидация применяется к authority, извлечённым из `request.url`.

**Тесты:**
- Тесты схемы покрывают: корректный `https://`, отвергнутый `http://`, отвергнутый `ftp://`, отвергнутый URI с пустой схемой.
- Тесты authority покрывают: корректный `host`, корректный `host:port`, отвергнутый пустой, отвергнутый с префиксом схемы, отвергнутый с пробелами, отвергнутый с путём, отвергнутый с запросом, отвергнутый с фрагментом.

## Дополнительно

- Тесты: unit-тесты на конструкторы `HttpClientTransport` и `OhttpRequestData`, покрывающие каждый класс принятых/отвергнутых входов. Никаких изменений в example или README — реструктуризация L-01 уже переписала пример, чтобы демонстрировать только новые (без обхода) пути интеграции.
- Зависит от L-01 (типы `HttpClientTransport` и `OhttpRequestData` не существуют до того, как приземлится реструктуризация).
- Согласовать именование исключений с L-03: если L-03 приземлится первой, использовать её иерархию `OhttpException` напрямую. Если эта задача приземлится первой, ввести временное библиотечное исключение, которое L-03 затем вольёт в иерархию.
- Источник: половина оригинальной L-01, связанная с обходом приватности (M-01 в `../merged-tasks/`), **отброшена** — реструктуризация удаляет `sendDirect()` и `OhttpGatewayConfig.directBaseUrl`. Половина с валидацией входов (M-02) сохраняется, перенацеленная как описано выше.
