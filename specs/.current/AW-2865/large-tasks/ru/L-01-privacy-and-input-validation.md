# Фундамент приватности и валидации входных данных для `OhttpGatewayConfig` / `sendDirect`

**Оценка:** 3 дня
**Приоритет:** P1: Critical
**Компонент:** App
**Серьёзность:** BLOCKER

## Описание задачи

`OhttpGatewayConfig` и сопутствующий хелпер `sendDirect()` находятся на границе доверия между кошельком и relay/шлюзом. Два усугубляющих друг друга дефекта открывают «грабли» для приватности, которые должны быть закрыты вместе до того, как будут запущены любые другие follow-up задачи:

1. **Тихий обход приватности в `sendDirect`.** Когда `OhttpGatewayConfig` создаётся без опционального `directBaseUrl`, последующий вызов `sendDirect()` отправляет открытый HTTP-запрос напрямую на хост relay — без шифрования, без unlinkability, без какого-либо сигнала в рантайме о том, что OHTTP-поток был обойдён. Тихий fallback `directBaseUrl ?? gatewayBaseUrl` в `lib/src/ohttp_client.dart:52` превращает «сравнительный» хелпер в мину для приватности, расширенную дополнительно публичным геттером `effectiveDirectBaseUrl` на той же строке. Для некастодиального крипто-кошелька это разница между не-линкуемым RPC-вызовом и утечкой активности кошелька оператору relay в открытом виде. Файл примера `example/ohttp_dart_example.dart` ни о чём из этого не предупреждает.

2. **Нет валидации схемы `gatewayBaseUrl` и формы `targetAuthority`.** Оба поля принимаются как сырые `String` без валидации. Библиотека молча принимает URL вида `http://` — RFC 9458 §1 требует TLS на внешнем канале — после чего внешний OHTTP-шифротекст передаётся в открытом виде, давая пассивному наблюдателю на пути возможность корреляции по таймингу с шлюзом и подрывая свойство unlinkability, ради которого OHTTP и существует. `targetAuthority` принимает любую строку, поэтому неверное значение (`"https://host"`, пробелы в начале/конце, встроенный путь) молча приводит к некорректному внутреннему BHTTP-запросу.

Вызывающая сторона кошелька с опечаткой в конфигурации или с неправильно настроенным staging-URL не получает никакого сигнала о том, что развёртывание сломано — до тех пор, пока сетевой наблюдатель уже не начнёт перехватывать трафик, либо пока шлюз не вернёт ошибку парсинга внутреннего запроса.

## Технические детали

Все изменения вносятся одновременно в `OhttpGatewayConfig` / `OhttpClient.sendDirect()` (`lib/src/ohttp_client.dart`) плюс в файл примера.

### Часть A — Закрыть обход приватности в `sendDirect`

**1. `sendDirect()` больше не обходит OHTTP молча** (`lib/src/ohttp_client.dart:147-171`)

Метод `sendDirect()` сейчас несёт лишь одну строку документации («Send a direct HTTP request (for comparison).»), без `@Deprecated`, без `assert` и без предупреждения о влиянии на приватность. Тело на строках 148–171 вызывает `_httpClient.send()` по `effectiveDirectBaseUrl`, который превращается в `gatewayBaseUrl`, если `directBaseUrl` равен null.

Требуется:
- Метод должен fail-fast (через assertion или брошенное библиотечное исключение), когда `directBaseUrl` равен null или равен `gatewayBaseUrl` — никогда не отправлять открытый трафик на relay молча.
- Добавить аннотацию `@Deprecated('...')`, явно называющую влияние на приватность.
- Документация к методу должна явно сообщать, что вызов `sendDirect()` полностью обходит OHTTP-конвейер — никакого HPKE-шифрования внутреннего запроса, никакой relay-индирекции, никакой unlinkability — и должна перечислять гарантии из RFC 9458 §1, от которых вызывающая сторона отказывается, выбрав этот путь (конфиденциальность внутреннего запроса от оператора relay, unlinkability между идентичностью клиента и содержимым запроса, изоляция метаданных от того, как целевой сервер видит клиента).

**2. Удалить или перевести в private публичный геттер `effectiveDirectBaseUrl`** (`lib/src/ohttp_client.dart:52`)

Сейчас этот геттер — публичная поверхность, делающая тихий fallback обнаружимым. Переименовать в `_effectiveDirectBaseUrl` (library-private) или встроить логику разрешения непосредственно в тело `sendDirect()` на строке 154, чтобы публичная поверхность вообще не раскрывала fallback по имени. Обновить doc-комментарий конструктора, чтобы он больше не упоминал fallback-путь как публичное понятие.

**3. Переработать файл примера** (`example/ohttp_dart_example.dart`)

- В основном потоке демонстрировать только `send()`.
- Если `sendDirect()` вообще показывается, обернуть его громким комментарием «не использовать в проде — обходит OHTTP» и требовать явный `directBaseUrl`, отличный от `gatewayBaseUrl`.
- Добавить doc-комментарии, объясняющие смысл каждого поля `OhttpGatewayConfig`, особенно `targetAuthority` (приватно-чувствительный backend-хост, встроенный во внутренний BHTTP-конверт).
- Перечислить исключения, которые вызывающая сторона должна ожидать обработать.
- Сослаться на RFC 9458 §1 для гарантий unlinkability, на которые опирается пример.

### Часть B — Валидация входов `OhttpGatewayConfig`

Две связанные проверки выполняются во время конструирования `OhttpGatewayConfig` (`lib/src/ohttp_client.dart:43-51`):

**4. Принудительное использование схемы HTTPS**

Конструктор (строки 43–50) и места вызова, собирающие URI из этих полей (строка 82 для GET KeyConfig, строка 116 для POST на шлюз), сейчас принимают любую схему. Отвергать любой базовый URL, схема которого не `https://`, как для `gatewayBaseUrl`, так и для `directBaseUrl` (когда задан). Бросать библиотечное исключение во время конструирования. Документировать обоснование (RFC 9458 §1) в doc-комментарии конструктора.

Если нужен escape hatch для тестов — закрыть его явным именованным флагом (например, `allowInsecureScheme: false` по умолчанию), чтобы production-код не мог случайно через него проскочить.

**5. Валидация формы `targetAuthority`** (`lib/src/ohttp_client.dart:97-104`)

`targetAuthority` встраивается дословно во внутренний BHTTP-запрос в `bhttp.serializeRequest(...)` (строки 97–104). Допустимая форма — продукция `authority` из RFC 3986: `host` или `host:port`. Отвергать:
- пустые значения,
- значения с префиксом схемы (`http://`, `https://` и т.д.),
- значения с пробелами,
- значения с символами пути или запроса (`/`, `?`, `#`),
- значения с символами фрагмента.

Бросать библиотечное исключение во время конструирования. Документировать ожидаемую форму в doc-комментарии конструктора со ссылкой на RFC 3986 §3.2.

## Критерии приёмки

**Обход приватности в sendDirect:**
- Вызов `sendDirect()` без явного `directBaseUrl`, отличного от `gatewayBaseUrl`, fail-fast (assertion или библиотечное исключение), никогда не отправляя открытый трафик на relay молча.
- Doc-комментарий `sendDirect()` называет влияние на приватность (нет шифрования, нет unlinkability) и ссылается на гарантии RFC 9458 §1, которые обходятся.
- На методе присутствует аннотация `@Deprecated` (или эквивалентный сигнал во время компиляции).
- `effectiveDirectBaseUrl` больше не является частью публичного API `OhttpGatewayConfig`; внутренние вызовы продолжают работать.
- Doc-комментарий `OhttpGatewayConfig` больше не упоминает fallback-путь как публичное понятие.
- Основной поток `main()` в файле примера использует только `send()`; любая ссылка на `sendDirect()` сопровождается заметным предупреждением и требует явный `directBaseUrl`.
- Doc-комментарии примера перечисляют каждое поле `OhttpGatewayConfig` и ожидаемую поверхность исключений.

**Валидация входных данных:**
- Конструирование `OhttpGatewayConfig` с `http://` (или любым не-`https://`) `gatewayBaseUrl` бросает библиотечное исключение во время конструирования.
- Та же проверка схемы отвергает `http://` `directBaseUrl`, когда задан.
- Конструирование `OhttpGatewayConfig` с некорректным `targetAuthority` (пустой, с префиксом схемы, с пробелами, с путём) бросает библиотечное исключение во время конструирования.
- Doc-комментарий конструктора ссылается на RFC 9458 §1 для требования схемы и на RFC 3986 §3.2 для формы authority.

**Тесты:**
- Unit-тест проверяет конфигурацию `sendDirect` с тихим fallback и утверждает, что вызов отвергается.
- Тесты валидации схемы покрывают: корректный `https://`, отвергнутый `http://`, отвергнутый `ftp://`, отвергнутая пустая строка.
- Тесты валидации authority покрывают: корректный `host`, корректный `host:port`, отвергнутый пустой, отвергнутый с префиксом схемы, отвергнутый с пробелами, отвергнутый с путём.
