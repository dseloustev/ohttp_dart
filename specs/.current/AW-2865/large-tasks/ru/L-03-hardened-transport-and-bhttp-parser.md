# Защищённый транспорт: HTTP-таймауты, кэширование KeyConfig, нормализация URL + границы/ограничения парсера BHTTP

**Оценка:** 4 дня
**Приоритет:** P2: High
**Компонент:** App
**Серьёзность:** HIGH

## Описание задачи

Два парных направления работ по устойчивости к некорректно ведущему себя или вредоносному шлюзу. Оба бросают новые типизированные исключения в иерархию `OhttpException`, введённую в L-02; выполнение их вместе сохраняет поверхность конфигурации (таймауты, ограничения) консолидированной в одной структуре опций, а не перетряхиваемой дважды.

**Сетевая часть — у `OhttpClient.send()` три независимых пробела:**

1. Ни GET KeyConfig (`_httpClient.get(...)` в `lib/src/ohttp_client.dart:81-83`), ни POST на шлюз (`_httpClient.post(...)` на строках 115–119) не имеют цепочки `.timeout(...)`. Не отвечающий шлюз может бесконечно подвесить `await`. Для интерактивного UI кошелька это проявляется как замёрзший экран без индикации прогресса и без аварийного выхода.
2. Нет кэша KeyConfig. Каждый `send()` запускает свежий discovery GET (строки 81–89), удваивая количество round-trip для каждого RPC-вызова (обновление баланса, список транзакций, оценка комиссии). Для кошелька, делающего много вызовов подряд, это удваивает задержки и трафик без какой-либо пользы — KeyConfig это долгоживущий материал, который шлюз намеренно ротирует редко.
3. Композиция URL выполняется конкатенацией строк в трёх местах вызова (`lib/src/ohttp_client.dart:82, 116, 154`) без нормализации слешей. `gatewayBaseUrl: 'https://gw.example/'` плюс `configPath: '/key'` даёт `https://gw.example//key` — двойной слеш, который строгий reverse-proxy может отвергнуть. Зеркальный случай (нет завершающего слеша на базе, нет ведущего слеша в пути) даёт путь, в котором разделитель отсутствует.

**Часть парсера — у `lib/src/bhttp.dart` четыре пересекающихся дефекта:**

1. **`RangeError` вместо `FormatException`**: `decodeVarint` (строки 44–67) и вызовы `sublist` на строках 173, 178 и 187 бросают `RangeError` на усечённом входе. `RangeError` — это `Error`, а не `Exception`, поэтому вызывающая сторона, оборачивающая парсинг BHTTP в `try { ... } on FormatException { ... }`, не поймает его, и программа упадёт.
2. **Нет ограничений на размер заголовков/тела ответа**: `parseResponse` (строки 164–187) читает `headersLen` и `contentLen` как сырые varint. Враждебный шлюз может объявить `headersLen = 2^30`, форсируя выделение ~1 ГиБ в `data.sublist(...)` на строке 173 или 178. Аналогично, клиентский `gatewayResponse.bodyBytes` передаётся в `ohttpDecapsulate` в `lib/src/ohttp_client.dart:129-133` без проверки длины. На мобильном кошельке даже sub-OOM выделение в сотни МиБ достаточно, чтобы убить приложение.
3. **Нет ограничения на размер входов `serializeRequest`**: строки 74–111 не накладывают верхнюю границу на `method`, `scheme`, `authority`, `path`, `headers` или `body` перед varint-кодированием.
4. **Нет валидации диапазона status-кода**: строки 148–162 читают `statusCode` как сырой varint и только пропускают информационные ответы `1xx`. Некорректный или вредоносный ответ шлюза может нести статус 999, 0 или `2^62 - 1`, и `parseResponse` спокойно его вернёт.

Ссылки на RFC: RFC 9292 §3.3 (фрейминг), §3.5.3 (фрейминг ответов), §3.5.4 (varint через RFC 9000 §16); RFC 9110 §15 (диапазон status-кодов); RFC 9458 §1 (транспорт).

## Технические детали

### Часть A — Сетевая часть (`lib/src/ohttp_client.dart`)

**1. Настраиваемые таймауты** (`lib/src/ohttp_client.dart:81-83, 115-119`)

Добавить цепочки `.timeout(...)` к обоим HTTP-вызовам в `OhttpClient.send()`. Позволить вызывающей стороне переопределять через `OhttpGatewayConfig` (или новую форму `OhttpClientOptions`) с разумными значениями по умолчанию. Документировать значения по умолчанию. По таймауту бросать `OhttpTimeoutException` из иерархии L-02.

Отдельно принять решение о семантике retry — как минимум задокументировать отсутствие автоматических повторов и ответственность вызывающей стороны.

**2. Кэш KeyConfig с TTL** (`lib/src/ohttp_client.dart:69-89`)

У `OhttpClient` сейчас есть только поля `_httpClient` и `gateway`. Добавить поле кэша `KeyConfig?` с настраиваемым TTL. Попадания в кэш закорачивают discovery GET. При сбое запроса, который намекает на устаревший конфиг (специфичный код ошибки шлюза или сбой аутентификации AEAD на ответе), инвалидировать кэш и один раз повторить discovery.

- TTL настраивается через структуру опций; значение по умолчанию должно отражать реалистичную частоту ротации ключей и быть задокументировано.
- Конкурентность: Dart однопоточный по изолятам; простой защищённый `Future<KeyConfig>` достаточен, чтобы перекрывающиеся вызовы `send()` разделяли одну in-flight операцию.

**3. Нормализация путей URL** (`lib/src/ohttp_client.dart:82, 116, 154`)

Три места вызова сейчас конкатенируют строки:
- Строка 82: `Uri.parse('${gateway.gatewayBaseUrl}${gateway.configPath}')`
- Строка 116: `Uri.parse('${gateway.gatewayBaseUrl}${gateway.requestPath}')`
- Строка 154: `Uri.parse('${gateway.effectiveDirectBaseUrl}$path')` (или его private-заменитель, в зависимости от результата L-01)

Ввести единый хелпер, нормализующий обработку слешей (все четыре случая: база с/без завершающего слеша × путь с/без ведущего слеша) и валидирующий, что собранный `Uri` корректен перед возвратом. Все три места вызова делегируют в хелпер.

### Часть B — Защита парсера BHTTP (`lib/src/bhttp.dart`)

**4. Хелпер для bounds-check** (`lib/src/bhttp.dart:44-67, 173, 178, 187`)

Ввести приватный хелпер (например, `_requireBytes(data, offset, n)`), который бросает `FormatException` с понятным сообщением при `offset + n > data.length`. Применять его перед каждым индексированным чтением (`data[offset]`, `data[offset + i]`) и вызовом `sublist(...)` в `decodeVarint` и в путях парсинга ответа/запроса. Изменение механическое и локализованное; никаких изменений API кроме замены `RangeError` на `FormatException` для этих конкретных мест вызова.

**5. Ограничения размера ответа** (`lib/src/bhttp.dart:164-187`, `lib/src/ohttp_client.dart:129-133`)

Применить два слоя ограничений с разумными значениями по умолчанию, подходящими для wallet RPC payload (максимум однозначные МиБ), оба настраиваются через ту же структуру опций, что и Часть A:

- Слой BHTTP: в `parseResponse` проверять `headersLen` и `contentLen` относительно настроенных верхних границ перед выделением. Отвергать чрезмерные объявления с `FormatException` (через хелпер из шага 4).
- Слой клиента OHTTP: в `OhttpClient.send` (строки 129–133) проверять `gatewayResponse.bodyBytes.length` относительно настроенной верхней границы перед передачей в `ohttpDecapsulate`. Отвергать через `OhttpParseException` (из иерархии L-02).

**6. Ограничения размера запроса** (`lib/src/bhttp.dart:74-111`)

Применить настраиваемые верхние границы на входы `serializeRequest` (`method`, `scheme`, `authority`, `path`, количество и длины имён/значений заголовков, длина `body`) перед началом сериализации. Отвергать чрезмерные входы с типизированным библиотечным исключением. Значения по умолчанию консервативны и задокументированы; wallet RPC payload редко превышает несколько сотен килобайт.

**7. Валидация диапазона status-кода** (`lib/src/bhttp.dart:148-162`)

После чтения финального (неинформационного) status-кода валидировать, что он попадает в 100–599 включительно (RFC 9110 §15). Бросать `FormatException` для выходящих за диапазон значений. Документировать ограничение в doc-комментарии `parseResponse`.

**9. Тесты парсера** (`test/bhttp_test.dart`):
- Усечённый вход в каждом упомянутом смещении: однобайтовая граница varint, 2/4/8-байтовые границы varint, имя заголовка, значение заголовка, контент. Утверждать `FormatException` (не `RangeError`).

## Критерии приёмки

**Таймауты / кэширование / URL:**
- Оба вызова `_httpClient.get` и `_httpClient.post` в `OhttpClient.send` имеют цепочку `.timeout(...)` с настраиваемой длительностью.
- Таймаут по умолчанию задокументирован в doc-комментарии `OhttpGatewayConfig` (или `OhttpClientOptions`); таймаут производит `OhttpTimeoutException`.
- `OhttpClient` раскрывает поле кэша и конфигурацию TTL для разобранного `KeyConfig`; первый `send()` заполняет кэш; последующие вызовы `send()` в пределах TTL пропускают discovery GET.
- TTL настраивается, значение по умолчанию отражает реалистичную частоту ротации ключей; политика инвалидации кэша задокументирована.
- Единый хелпер обрабатывает композицию URL для GET KeyConfig, POST на шлюз и direct-send; он обрабатывает все четыре комбинации слешей и валидирует результат.

**Парсер BHTTP:**
- Все операции `data[offset]`, `data[offset + i]` и `data.sublist(...)` в парсере BHTTP проходят через общий хелпер bounds-check или эквивалентную защиту и бросают `FormatException` (никогда `RangeError`) при усечении.
- `try { ... } on FormatException { ... }` корректно ловит любой сценарий усечения.
- `parseResponse` отвергает секции заголовков и контент больше настроенных ограничений с `FormatException`; значения по умолчанию консервативно низкие и задокументированы.
- `OhttpClient.send` отвергает ответы шлюза больше настроенного ограничения до парсинга.
- `serializeRequest` отвергает входы, превышающие настроенные верхние границы для method/scheme/authority/path/headers/body length, с типизированным библиотечным исключением.
- `parseResponse` отвергает status-коды вне 100–599 с `FormatException`; doc-комментарий ссылается на RFC 9110 §15.

**Тесты:**
- Unit-тесты покрывают каждый сценарий, перечисленный в разделе «Тесты» выше.
- Попадание в кэш должно наблюдаться в тестах как «ноль HTTP-вызовов на endpoint configPath».

## Дополнительно

- Поверхность конфигурации ограничений размера и таймаутов должна быть консолидирована в одном месте (`OhttpGatewayConfig` или новая `OhttpClientOptions`), чтобы эта и будущие задачи разделяли одну структуру опций.
- Эта задача зависит от L-02 (использует `OhttpTimeoutException`, `OhttpParseException`, а ограничения размера от защиты парсера могут координироваться с типизированной поверхностью исключений для `OhttpClient.send`).
- Дополнения BHTTP-тестов из L-05 (случаи усечения, утверждающие `FormatException`) предполагают, что работа по защите парсера в этой задаче приземлилась.
- Исходные merged-задачи (в `../../merged-tasks/`): M-06 (таймауты/кэширование/URL), M-07 (защита парсера BHTTP).
