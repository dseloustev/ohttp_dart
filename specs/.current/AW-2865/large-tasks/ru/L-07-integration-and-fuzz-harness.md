# Интеграционный тест против шлюза и fuzz / property-based harness

**Оценка:** 2 дня
**Приоритет:** P2: High
**Компонент:** App
**Серьёзность:** HIGH

## Описание задачи

В тестовом наборе два структурных пробела покрытия, которые усиливают друг друга:

1. После L-01 существующие тесты (`bhttp_test`, `hpke_test`, `ohttp_test`, плюс новые `key_config_cache_test`, `ohttp_session_test`, `adapters/http_adapter_test`) прорабатывают отдельные слои или куски оркестрации изолированно. Ни один из них не прогоняет **полную интеграцию**: `OhttpHttpClient.send` (или путь более низкого уровня `OhttpSession.send`) сквозным образом против заглушенного шлюза, отвечающего и на KeyConfig GET, и на encapsulated POST. Регрессия, ломающая оркестрацию (композиция URL, прокидывание заголовков, обработка content-type, кэширование KeyConfig, таймауты, привязка observer), не была бы поймана существующими unit-тестами. Для библиотеки, ценность которой — корректность против внешней стороны, минимальное покрытие — это интеграционный тест против заглушенного шлюза.
2. Существующие тесты покрывают векторы RFC и небольшой набор подобранных вручную негативных случаев, но нет property-based или fuzz-покрытия varint-кодека, парсера BHTTP или парсера KeyConfig. Патологические входы, сконструированные атакующим — это именно та поверхность, для покрытия которой и предназначено fuzz-тестирование. Свойства вроде «encode-decode varint — это identity» и «любой вход в `parseResponse` либо парсится успешно, либо бросает `FormatException`» сейчас не задействуются в масштабе.

Эта задача создаёт директорию и harness, которые будущие тесты смогут расширять.

## Технические детали

### Часть A — Интеграционный тест против заглушки шлюза

**1. Новая директория `test/integration/`**

Директории `test/integration/` сейчас не существует. Создать её и добавить как минимум один тест, подключающий `OhttpHttpClient` к локальной in-process заглушке. Рекомендуемый подход (без новой dev-dep):

**MockClient из `package:http/testing.dart`**. Пакет уже зависит от `http ^1.6.0`, который транзитивно предоставляет `MockClient` — никакой новой зависимости не требуется. Интеграционный тест конструирует `OhttpHttpClient`, подключённый через `HttpClientTransport`, подключённый через `MockClient`, который:

- Отвечает на `keysUrl` синтетическим 41-байтовым KeyConfig (key_id || X25519 KEM || 32-байтовый pubkey || symLen=4 || HKDF-SHA256 || AES-128-GCM).
- Отвечает на POST-ы к `gatewayUrl`, парся encapsulated request ровно настолько, чтобы провалидировать wire-формат, а затем возвращая заранее заготовленный зашифрованный ответ, который decap успешно развернёт (или намеренно malformed для сценариев сбоя).

Это более дешёвый вариант. Полный crypto round-trip здесь сквозным образом не тестируется, потому что в этом пакете нет имплементации HPKE-receiver — заглушка не может зашифровать валидный OHTTP-ответ без неё. Два способа это обойти:

(а) Ограничить интеграционный тест **assertions оркестрации**, которые не требуют успешного decap: encapsulated request постится с правильным `Content-Type`, правильным путём, правильной формой тела; ошибки шлюза распространяются как правильные типизированные исключения; кэш инвалидируется на правильных событиях; события observer срабатывают с правильными полями. Тест оборачивает decap в `expectLater(..., throwsA(...))` и инспектирует то, что было отправлено.

(б) Добавить минимальный **внутритестовый helper HPKE-receiver** для шифрования заготовленного ответа теми же примитивами, которые библиотека выставляет. Это больше работы, но даёт настоящий round-trip интеграционный тест. Тот же helper уже существует в `test/ohttp_test.dart` (тест 7 из работы по OHTTP round-trip в L-06) — переиспользовать его.

Задокументировать выбор в `test/integration/README.md`. Вариант (б) поверх L-06 — рекомендуемый scope: helper уже существует.

Любой подход сохраняет CI герметичным (никаких реальных сетевых вызовов). Тест прорабатывает `OhttpHttpClient.send` сквозным образом и утверждает путь оркестрации: discovery KeyConfig → BHTTP-сериализация → OHTTP encapsulation → POST на шлюз → decapsulation → парсинг BHTTP-ответа.

**Кросс-задачные assertions, которые интеграционный тест должен покрывать:**
- Типизированные типы исключений L-03 срабатывают на соответствующих путях сбоя: 4xx шлюза → `OhttpHttpException`(4xx) из `HttpClientTransport`; сбой AEAD → `OhttpDecryptionException` из `OhttpSession.send`.
- Таймауты L-04: `MockClient` с задержанным ответом выше сконфигурированного `gatewayTimeout` → `OhttpTimeoutException`.
- Проверка response-cap из L-04: заглушка возвращает тело выше cap → `OhttpParseException`.
- Кэширование L-01 + L-05: первый `send()` триггерит `onKeyConfigFetch`; второй `send()` в пределах TTL триггерит `onKeyConfigCacheHit`, а `MockClient` увидел только один GET на `keysUrl`.
- События observer L-05 срабатывают с задокументированными полями на каждом потоке (успех и каждый тип сбоя).

### Часть B — Fuzz / property-based тесты

**2. Property-based или fuzz слой**

Два практических варианта:

(а) Использовать совместимый с Dart пакет, такой как `glados` (добавляет `dev_dependency`).
(б) Самописные рандомизированные генераторы с фиксированным CI seed.

Добавить как минимум три property-теста:

- **Identity round-trip varint** над случайными значениями в `[0, 2^62)`. Для каждого сгенерированного значения `decodeVarint(encodeVarint(v))` должно равняться `v`, а закодированная форма должна совпадать с ожидаемой длиной для диапазона значения.
- **`parseResponse(randomBytes)` никогда не бросает ничего, кроме `FormatException`** (координируется с защитой парсера BHTTP из L-04, конвертирующей `RangeError` в `FormatException`).
- **`OhttpKeyConfig.parse(randomBytes)` никогда не бросает ничего, кроме типизированных библиотечных исключений** — конкретно `OhttpKeyConfigException` или `OhttpUnsupportedSuiteException` (из L-03). Случайные байты, которые случайно парсятся успешно — это нормально.

CI seed зафиксирован для воспроизводимости; возможность варьировать seed для периодических глубоких прогонов должна быть задокументирована. Ни один тест не должен превышать нескольких секунд за прогон CI; ограничить количество итераций соответственно.

Любой новый тип исключения, всплывший на fuzz-входах, должен быть триажен и либо исправлен, либо добавлен в задокументированную поверхность исключений.

## Критерии приёмки

- Директория `test/integration/` существует с как минимум одним тестовым файлом и `README.md`, документирующим выбранный подход заглушки (`MockClient`-based, с внутритестовым helper-receiver или без).
- Интеграционный тест прорабатывает `OhttpHttpClient.send` (или `OhttpSession.send`) сквозным образом против заглушенного шлюза на базе `MockClient`, покрывая discovery KeyConfig → BHTTP serialize → OHTTP encap → POST на шлюз → decap → парсинг BHTTP.
- Интеграционный тест утверждает:
  - Типизированные типы исключений L-03 срабатывают на ожидаемых путях сбоя (4xx/5xx шлюза, сбой AEAD).
  - Таймауты L-04 срабатывают с `OhttpTimeoutException` при превышении сконфигурированного таймаута.
  - Отбраковка по response-cap L-04 с `OhttpParseException` на превышающих размер ответах заглушки.
  - `KeyConfigCache` из L-01 закорачивает в пределах TTL (наблюдаемо как ноль GET-ов на `keysUrl` на втором `send()`).
  - События `OhttpObserver` из L-05 срабатывают с задокументированными полями на успешных и сбойных потоках.
- CI прогоняет интеграционный тест без доступа к внешней сети.
- Добавлено как минимум три property/fuzz-теста: identity round-trip varint, инвариант `parseResponse` для случайных байт (бросает только `FormatException`), инвариант `OhttpKeyConfig.parse` для случайных байт (бросает только типизированные библиотечные исключения из L-03).
- Конфигурация CI использует фиксированный seed для воспроизводимости; механизм переопределения seed для более глубоких периодических прогонов задокументирован.
- Ни один тест не идёт дольше нескольких секунд за прогон CI.
- Любые новые типы исключений, всплывшие на fuzz-входах, задокументированы в соответствующих doc-комментариях или — если неожиданны — исправлены.

## Дополнительно

- Тесты: интеграционные тесты + property/fuzz-тесты, оба запускаются через `dart test`.
- `MockClient` уже доступен транзитивно через существующую зависимость `http: ^1.6.0` — **никакой новой dev-dep не требуется** для интеграционного теста (это изменение относительно оригинальной L-06, где `shelf` рассматривался как вариант). `glados` остаётся опциональной dev-dep для property-тестов, если команда предпочтёт его самописным генераторам — скоординировать перед добавлением в `pubspec.yaml`.
- Эта задача должна приземлиться последней, потому что она утверждает поведение, установленное L-01 (вся новая публичная поверхность), L-03 (типизированные исключения), L-04 (таймауты, ограничения) и L-05 (события observer).
- Исходные merged-задачи (в `../merged-tasks/`): M-12 (интеграция + fuzz). Цель интеграционного теста меняется с `OhttpClient` на `OhttpHttpClient` (или `OhttpSession.send`); рекомендация по подходу заглушки сдвигается с «сервер `shelf`» на «`MockClient` + переиспользование внутритестового helper-а HPKE-receiver из L-06».
